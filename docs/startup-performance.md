# 启动提示与菜单卡顿修复

## 启动兼容

原 `launch.exe` 传递十六进制窗口句柄作为首个参数。直接运行 `wf.exe` 或传入 `0` 都可能弹出“建议使用 launch.exe”的原生提示，阻止游戏继续初始化，后面的渲染窗口此时可能呈空白。

`tools/OfflineLauncher.cs` 创建仅处理消息的隐藏窗口，传递有效句柄后启动当前目录的独立 `game/wf.exe`。它没有可见界面，也不访问网络，不改游戏 EXE 或资源包。用户关闭游戏后，适配器在一秒内结束。`tools/build_launcher.py` 使用 Windows 自带的 .NET Framework 4 编译器生成适配器；构建和部署入口均使用同一 CMD 模板。

更正：此前测试无法排除测试期间人工确认警告的影响。用户在 `start_offline.cmd` 启动时仍遇到该警告，后续受控测试也复现了它，因此隐藏窗口句柄方案尚未解决启动提示。保留此问题记录，避免将进入大厅误判为启动提示修复成功。

## 离线提示

大厅未恢复功能使用的提示回调改为无操作，点击后保持当前页面。英雄页的攻略等入口也复用这一回调。实际点击攻略入口后，没有离线功能确认框，原页面保留。

## 重复工作消除

- 原版 SuitObj 的 `item` getter 使用 `dict.get(id, FashionItem(...))`，即使命中已有数据也会创建默认对象。本地 SuitObj 改为按实例缓存原 FashionItem。
- 全英雄时装列表只在首次构建时汇总，后续进入与切换英雄复用同一目录；原品质筛选和分页控件保留。
- 进出英雄页只确保当前玩家数据结构，不再反复重建所有时装对象。
- 已处于当前页签时不重复初始化；预览模型已有真实行为时不重新绑定，显示后的模型不每半秒重复执行淡入。
- 大地图已经隐藏时不重复调用其可见性更新。

2026-10-13，同一客户端会话中的临时方法计时（毫秒，单轮样本）：

| 操作 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 重复进入时装页的 enter 处理 | 131 | 23 |
| 重复选择当前时装页的 set_tab 处理 | 132 | 0 |
| 时装页内切到英雄 4 的 select 处理 | 155 | 31 |
| 时装页内切回英雄 3 的 select 处理 | 152 | 56 |

这些数字是客户端 Python 方法的耗时，不是整帧渲染或磁盘加载时间。首次模型、贴图及动画加载仍可能有停顿，不能由此断言所有“未响应”现象已消失。临时计时代码不包含在部署版本中。

用户连续打开英雄／时装并切换角色后反馈“明显顺畅了”。部署版本复测六个页签均无初始化异常，角色模型与行为就绪，最终能返回大厅。
