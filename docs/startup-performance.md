# 启动提示与菜单卡顿修复

## 启动兼容

本地旧 `launch.exe` 的 `%x %s` 实际传递的是进程 ID，与当前 1.0.192 客户端参数解析方式不匹配。当前客户端通过 `-redirect <十进制窗口句柄>` 设置启动端点并检查 `IsWindow`。无端点或端点无效会弹出“建议使用 launch.exe”的原生提示，阻止初始化，后面的渲染窗口此时可能呈空白。

`tools/OfflineLauncher.cs` 创建无可见界面的消息端点，明确使用 `-redirect` 传递有效句柄，再启动当前目录的独立 `game/wf.exe`。它不访问网络，不改变原游戏 EXE 或资源包。用户关闭游戏后，适配器自动结束。`tools/build_launcher.py` 使用 Windows 自带的 .NET Framework 4 编译器在客户端根目录生成 `launch.exe`；构建和部署入口均使用同一 CMD 模板。

此前传裸句柄、进程 ID、改窗口类名的方案均复现警告。最终按当前客户端的实际解析方式修正后，在没有点击警告的情况下直接进入大厅，窗口列表只有游戏主窗口。2026-10-14 已通过最终启动脚本复测。

## 离线提示

大厅未恢复功能使用的提示回调改为无操作，点击后保持当前页面。英雄页的攻略等入口也复用这一回调。实际点击攻略入口后，没有离线功能确认框，原页面保留。

## 重复工作消除

- 原版 SuitObj 的 `item` getter 使用 `dict.get(id, FashionItem(...))`，即使命中已有数据也会创建默认对象。本地 SuitObj 改为按实例缓存原 FashionItem。
- 全英雄时装列表只在首次构建时汇总，后续进入与切换英雄复用同一目录；原品质筛选和分页控件保留。
- 进出英雄页只确保当前玩家数据结构，不再反复重建所有时装对象。
- 已处于当前页签时不重复初始化；预览模型已有真实行为时不重新绑定，显示后的模型不每半秒重复执行淡入。
- 大地图已经隐藏时不重复调用其可见性更新。
- 离线初始化时阻止大地图打开入口与后续可见性请求，菜单切换前就保持隐藏，无需等定时器隐藏闪现的地图。
- 再次进入菜单时保留原预览空间和角色实体，关闭页面后隐藏预览，避免每次销毁并重新加载整套场景。
- Z/X/C/V 直接进入目标页，避免先加载上次页签再切页。
- 原背包复用 56 个格子，按分类和页码创建物品对象；客户端物品表共 13,122 条，未添加逐帧目录扫描。

用户连续打开英雄／时装并切换角色后反馈“明显顺畅了”。部署版本复测六个页签均无初始化异常，角色模型与行为就绪，最终能返回大厅。

## 2026-10-14 后续卡顿和输入修复

用户仍反馈经常停顿，继续排查后发现原 ActorField 每次进入强制切换高清、阴影、布料配置，离开时再次应用用户配置。离线入口改为复用原空间、模型及当前渲染配置，不执行这组临时画质切换；预览退出时仍停止特效、声音和位置回调，恢复大厅人物行为。保留已选择的预览英雄，避免重开同一页时再次加载相同模型。

大厅时装更新先比较原 root_fashions；未变化时不调用 set_fashions。切换英雄或首次加载档案仍明确应用外观。状态文件写入合并到后续帧，诊断命令只在修改时间变化后读取；启动时忽略上次调试遗留的命令。原 limitForegroundFPS 设置为 80，降低无上限渲染负载。

一轮原游戏方法计时：重复打开英雄页约 14 ms，重复打开时装页约 30 ms，退出约 2–3 ms，定时处理约 0–1 ms；首次建立时装页约 121 ms。数值来自临时诊断探针，只覆盖脚本处理，不代表整帧渲染、磁盘加载或所有英雄素材，不能据此宣称全部卡顿已经消失。临时探针不部署到成品。

视角问题源于 keepNormalizedPitch 在更改俯仰范围时重新映射角度。大厅保存真实 pitch/yaw 并在切页、重新激活时恢复，关闭归一化和原 enablePlayerFade。出生位置使用原 minimap 的中心 X/Z=(52,178)，物理落地后约 Y=219.025。

原 SysBox 的 Escape 取消标识是 ESC，现已改用该标识；测试第二次 Esc 能取消。回车接入大厅 ChatCityNewDlg 输入并处理其焦点，打字时拦截菜单快捷键。背包格子接入原 ItemTipDict 和悬停传感器，按需缓存名称、描述、品质等提示数据。程序内测试验证角度在切页和焦点恢复后保持，聊天 Z 不打开菜单，原道具提示非空，未改变的外观重新应用次数为 0。

最终不含性能探针的部署版本再次通过这些程序内验证；六个原版页签及预览模型行为无初始化错误。用户连续使用 Z、X 开关菜单后反馈“明显改善”。

## 开始游戏入口、帧率与大厅分块预加载

`开始游戏.exe` 与 `start_offline.cmd` 放在一起，以自身目录定位脚本并隐藏命令行窗口。脚本仍恢复 EditorConf 模板，再启动同目录的 launch.exe；可移动整个客户端目录，路径中的中文及空格由引号保护。生成器分别缓存两个 C# 源文件的哈希，已有 launch.exe 不会阻止生成新入口。好友覆盖补丁也包含新入口。

原画质页的 `LimitFpsSetting` 是帧率步进滑条，原档位为 60、80、无限制。离线适配扩展为 60、80、120、144、165、240、无限制，默认 80，保留原设置窗口及其确定、取消流程。选择会调用 BigWorld.limitForegroundFPS，确定保存实际帧率到离线档案，取消恢复保存值；不把新索引写入只认识三档的原配置。垂直同步仍按用户选择保留，会影响实际帧率。设置窗口打开时，离线菜单快捷键不抢占输入，Esc 关闭设置并恢复大厅控制。

原加载页只等待当前位置视距范围完成。离线大厅初始化后针对当前 `zc_new01` 空间调用一次原 SpaceManager 已使用的 `BigWorld.loadSpaceChunks(spaceID)`，提前请求大厅其他分块；不请求战场、预览空间，不在移动或定时更新中重复请求。该原生 API 的请求耗时约 0.1 ms，资源随后由引擎加载；请求耗时不代表全部素材加载完成，也不能证明走路卡顿全部由磁盘读取引起。此改动可能增加初始加载和内存占用，首次贴图上传仍可能停顿。

复测七档数值、取消恢复、144 FPS 保存后重新加载和原大厅输入均通过。用户首次走动仍报告固定位置偶发卡顿；随后实际走动采样 45 秒，共 3,585 个回调间隔，X 范围约 26.1–80.4、Z 范围约 131.1–223.0，间隔中位数与 P95 都约 13 ms，最大 31 ms，无超过 60 ms 的间隔。用户同时反馈这次走过没有卡顿。这支持首次资源／渲染缓存开销的推测，但没有捕捉到最初那次卡顿，不能确定具体瓶颈，或宣称冷启动时已全部消除。回调间隔不是 GPU 帧耗时，临时采样代码不发布。

同期 45 条本地进程计数中读取峰值约 7.8 MB/s，私有工作集约 1.37–1.43 GB；峰值读取时人物在 (52.26,218.73,155.16)，附近采样间隔约 13 ms。说明移动期间仍有资源读取，但该轮没有对应停顿，不能直接用读取速率判定卡顿原因。
